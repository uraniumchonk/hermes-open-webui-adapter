# AGENTS.md — hermes_tool_filter

Instructions for an AI agent working in this repo. Read this before editing
code, touching `patches/`, or deploying.

## What this is

An SSE proxy between **Open WebUI** and **Hermes Gateway**. It sits at
`:9099`, routes per-port to the right Gateway upstream, and fixes the tool
memory problem on **two endpoints**:

```
Open WebUI → hermes_tool_filter :9099/<port>/v1 → Hermes Gateway :3000x → model
```

- **`/v1/chat/completions`** — client-side context. OWUI sends the full history
  every turn; you can edit/retry messages. No server-side compression.
- **`/v1/responses`** — server-side context. You send just the latest message;
  the Gateway reloads the full transcript (tool calls included) from its session
  DB via an `X-Hermes-Session-Id` header. Seamless Hermes context compression,
  continuous like TUI mode. No edit/retry (server-side session).

Both endpoints do the same core fix: Hermes runs tools correctly in the agent
loop, but OWUI only persists HTML tool cards inside assistant text. On the next
request that HTML is sent back as normal assistant content → the model forgets
tools or starts mimicking `<details>`. The proxy **enhances** outbound tool
progress into OWUI cards and **sanitizes** inbound cards into model-safe
`assistant` + `tool` roles.

## Management briefing — tell your human

If you (the agent) are reading this to take over or help with this project,
**brief your human on the standing maintenance it needs**. This is what actually
keeps it running (our proven approach):

1. **After every `hermes update`** — the patches in `patches/` may have been
   reverted or drifted. Run the grep verification (below); if any patch is
   missing, re-apply in order (`chat_completions_all` **before**
   `responses_session_id`) and restart the affected gateway profile.
2. **After a model (jinja template) or OWUI upgrade** — re-run
   `venv/bin/python extract_tags.py` to regenerate `special_tags.json`, then
   restart the filter.
3. **After any filter code change** — `git push` → pull on the other machine →
   `sudo systemctl restart hermes-tool-filter` on **both** machines. meowhome's
   OWUI actually routes to the **meowplace** filter, so updating one machine
   isn't enough.
4. **Restarting the filter severs in-flight requests** — if your human is
   mid-chat through OWUI, the current turn will drop. Warn them before
   restarting.
5. **Patches are references, not guaranteed applies** — line numbers drift on
   `hermes update`; some versions need a manual re-apply by hand.

## The patches (read this before touching `patches/`)

`patches/` holds **three reference patches** for the Hermes git repo at
`~/.hermes/hermes-agent` — the Gateway behaviour this proxy's features rely on.
They are **snapshots taken against Hermes v0.22.5**, not guaranteed clean
applies; the owner keeps the live, versioned copies elsewhere, so these can lag
behind. **Only patches the filter depends on belong here** — personal or
unrelated Hermes patches do not.

| Patch | Needed for |
|---|---|
| `api_server_chat_completions_all.patch` | tool cards: SSE `hermes.tool.progress` carries `arguments`+`result` (base64 redacted); Chat Completions history keeps `role=tool` / `tool_calls`, last **user** is the turn input |
| `api_server_responses_session_id.patch` | responses session continuity: `X-Hermes-Session-Id` → full transcript from SessionDB (DB beats body), sid markers stripped before the model |
| `prompt_builder_api_server_hint.patch` | Markdown allowed on api_server (OWUI tool cards / formatting) |

### Apply order (matters)

Both api_server patches touch `gateway/platforms/api_server_openai_routes.py`
(the session one also touches `api_server_response_admissions.py`) — apply
`chat_completions_all` **first**, then `responses_session_id`.

```bash
cd ~/.hermes/hermes-agent
git apply ~/hermes_tool_filter/patches/api_server_chat_completions_all.patch
git apply ~/hermes_tool_filter/patches/api_server_responses_session_id.patch
git apply ~/hermes_tool_filter/patches/prompt_builder_api_server_hint.patch
# then restart the affected gateway profile(s)
```

### Verify a patch is applied (grep)

```bash
cd ~/.hermes/hermes-agent
grep -c '_redact_progress_result' gateway/platforms/api_server_openai_routes.py      # >0 chat_completions_all
grep -c 'OpenAI-native tool result' gateway/platforms/api_server_openai_routes.py    # >0 chat_completions_all
grep -c 'provided_session_id' gateway/platforms/api_server_response_admissions.py    # >0 responses_session_id
grep -c '_strip_hermes_sid_markers' gateway/platforms/api_server_openai_routes.py    # >=6 responses_session_id
grep -c 'Markdown is allowed' agent/prompt_builder.py                                # >0 prompt_builder_hint
```

Don't use `X-Hermes-Session-Id` as the marker for the session patch — upstream
parses that header too.

### After `hermes update`

`hermes update` does stash → pull → stash pop. When the pop conflicts, re-apply
by hand. If upstream moved the code into new helpers or modules, keep upstream's
structure and inject the patch's behaviour there instead of restoring the old
inline code. **Always** re-run the grep verification + `py_compile` the touched
files + restart the gateway profiles afterward.

Re-exporting: the two api_server patches share a file, so a plain
`git diff HEAD -- <file>` mixes both. Split by hunk (`hermes-sid` /
`provided_session_id` / `_strip_hermes_sid_markers` hunks → `responses_session_id`;
redact / tool-role hunks → `chat_completions_all`), then check that both apply
in order on a clean HEAD worktree.

## Maintenance

### Regenerate special tags

After a **model** (jinja chat template) or **OWUI** (middleware) upgrade, the
neutralize list may be stale. Re-run:

```bash
cd ~/hermes_tool_filter
venv/bin/python extract_tags.py   # rewrites special_tags.json
```

The script reads the local Qwen jinja template + OWUI `middleware.py` and
regenerates `special_tags.json`. It has hardcoded local paths — edit them if the
model/OWUI location changes.

### Tests

```bash
cd ~/hermes_tool_filter
venv/bin/python -m pytest test_responses_session.py        # 35 tests, the marker logic
venv/bin/python -m py_compile *.py
```

Gateway-side tests live in the Hermes repo:
`~/.hermes/hermes-agent/tests/gateway/test_api_server.py` (run via
`scripts/run_tests.sh`). The `TestResponsesSessionIdHeader` class covers the
responses session-id + marker-strip behavior.

### Logs

`hermes_tool_filter.log` (next to `main.py`) and the journal both follow
`TOOL_FILTER_LOG_LEVEL` (default `INFO`: ~6 lines per chat request + 1 per tool
call). For full stream tracing set `TOOL_FILTER_LOG_LEVEL=DEBUG` (systemd
`Environment=`) and restart the filter. `kill -USR2 <pid>` appends a
thread/task dump to the log file at any level.

### Deploy (two machines)

Both machines run the filter as a systemd service and keep a git clone of this
repo. **GitHub is the primary sync path** (both have the same
`~/.ssh/id_ed25519_github` key).

| | meowhome (192.168.0.160) | meowplace (192.168.0.150) |
|---|---|---|
| filter service | `sudo systemctl restart hermes-tool-filter` | `sudo systemctl restart hermes-tool-filter` |
| gateway restart | user-level: `systemctl --user restart hermes-gateway-<profile>.service` | system-level: `sudo systemctl restart hermes-coder hermes-chatting` |
| Hermes venv | `.venv/bin/python` | `venv/bin/python` (no `.venv`) |

Standard sync:

```bash
# on the dev machine:
git push origin main
# on the other machine:
cd ~/hermes_tool_filter && git pull
sudo systemctl restart hermes-tool-filter
```

**Gotcha — restarting the filter from an agent session that routes through
:9099 kills your own in-flight model request.** The agent's model traffic goes
through the filter; a restart severs the current turn's SSE stream (the session
survives, the turn is interrupted). Prefer restarting from a non-filter shell
(CLI/terminal), or accept the current turn will drop.

**Gotcha — meowhome's OWUI (30010) chatting model hits the MEOWPLACE filter
(192.168.0.150:9099), not the local one.** When testing a filter change in OWUI,
update + restart **both** machines' filters or you'll keep seeing the old code.

## Key invariants (don't break these)

- **One sid marker per chat, on the FIRST assistant message only.** The filter
  embeds a marker only when the request carries none (`should_embed = sid is
  None`); continuation turns keep the single marker.
- **Extraction is a forward scan with early exit** — it reads the first
  assistant item with a valid marker and stops. The huge middle OWUI history is
  never read (that's the whole point of the light request).
- **The marker never reaches the model.** The filter drops the payload history
  (sends only `[last user]` + header), and the Gateway strips any stray marker
  (fenced code-block form included) before building history.
- **Marker format is a visible fenced code block**
  (`\n\n` + fence + `<!--hermes-sid:<id>-->` + fence) — the user wants to see it
  as a session tag, not a hidden comment. Stripping must remove the whole
  fence+marker+fence, leaving no empty code block.
- **Only assistant-role items are scanned for markers** — a marker in a user
  item is a paste, not a continuation signal (also blocks session fixation via
  a typed sid).
- **`test_*.py` stay gitignored** — local-only, not shipped.

## Known limitations

- **Pasting an old marked thread into a new chat** continues the old session
  (the first marker wins). Accepted for the single-user setup; a chat-id map or
  signed marker would fix it if it ever matters.
- **Responses mode can't edit/retry old messages** (server-side session) — by
  design, not a bug.
